Tier 0 · setup · core: everyone, today · about 10 min

Claude Desktop, Code tab

I can open a folder in the Code tab and get Claude to create a file in it.

Do

Where: the Claude Desktop app on your own laptop, then a session on a new, empty folder called claude-test in your Documents, in Manual.

  1. Download Claude Desktop from claude.com/download, install it, and sign in.

    You should see: the Claude window, signed in to the account with your paid plan.

  2. Click the Code button (</>) at the top left.

    You should see: a message box with a folder button under it. If it asks you to upgrade, your plan doesn't include the Code tab: tell the facilitator before the day.

  3. In Finder or File Explorer, make an empty folder called claude-test in your Documents.
  4. Click + New. In the bar under the message box, choose This computer, then the folder button and Open folder…, and pick claude-test.

    You should see: the folder button now says claude-test.

  5. In the same bar, the mode button says Auto: that's the default. Click it and choose Manual. Leave Bypass permissions alone.

    You should see: the button says Manual. No Auto in the list? Your plan or organisation hasn't turned it on; choose Manual all the same. A new session can start in Auto again, so check this button every time you click + New today.

    Next to it, the model button: choose Haiku for the exercises. It's fast and uses the least of your plan's allowance; Opus and Fable are slower and can use a day's allowance in a morning of exercises. Keep them for hard work later.

  6. Predict: you send the prompt below. Will the file just appear? Will Claude ask you first? Where on your computer will it go?
  7. Send it:
    Create a file called hello.txt that says hello.

    You should see: Claude shows the new file and asks before saving it. Accept. Then open claude-test in Finder or File Explorer: hello.txt is there. Not there? Check the folder button says claude-test, not another folder.

Proof
hello.txt exists in claude-test, and you opened it yourself.
Watch for
  • "It's the same as the chat tab." The Chat tab has no access to your files; the Code tab works in the folder you chose, and only there unless you allow more.
  • "I need to install developer tools first." Not for this. Git comes next, and only because the later lessons use it.

Tier 0 · setup · core: everyone, today · about 10 min

Git, Node and a GitHub account

I have git and Node.js installed and a GitHub account I can sign in to.

Do

Where: a session on your claude-test folder from install, in Manual.

  1. Predict: is git already on your computer? Most Macs have it, or offer to fetch it; most Windows PCs don't.
  2. In the message box, type this and send it. The ! means run this myself: the command runs straight away, without Claude and without asking, and the result appears in the conversation.
    !git --version

    You should see: git version and a number. Then skip to step 5.

  3. If it said command not found or nothing useful:
    • Mac: git comes with Apple's developer tools. Asking for git when they're missing makes macOS offer to install them in a pop-up: click Install and wait a few minutes. No pop-up? Send !xcode-select --install.
    • Windows: install Git for Windows from git-scm.com/downloads/win, accepting the defaults. Quit Claude Desktop and open it again afterwards, so it finds git.
  4. Send !git --version again. You should see: git version and a number. Still not found? Bring the message to the facilitator's helper.
  5. If you don't have a GitHub account, make one at github.com/signup. Use the email you'll use for work, and turn on two-factor sign-in when it offers. You should see: your profile at github.com/<your-username> when you're signed in.
  6. Send your GitHub username (not your password) to the facilitator, the way they asked for it.
  7. Check for Node.js: skills and scripts later in the course run on it, and it's the one other tool you need.
    !node --version

    You should see: a version such as v22.…. command not found? Ask Claude:

    Install the current LTS version of Node.js on this computer. Tell me each step before you run it.

    Approve each step as you read it (on a Mac it may ask for your password in a pop-up: that's macOS, type it there, never in the chat). Then quit Claude Desktop, open it again, and send !node --version once more.

Proof
!git --version and !node --version in the Code tab print versions, and the facilitator has your GitHub username.
Watch for
  • "Git and GitHub are the same thing." Git is the tool on your laptop and works with no account at all. GitHub is a website that stores copies of git repositories so people can share them.
  • "Commands need a terminal." A ! in the message box runs one for you, and Claude can see the result. Most of the day you will ask Claude to run commands and read them, not type them.

Do

  1. In the Code tab, open a session on claude-test and check the mode button says Manual.
  2. Predict: you ask Claude to copy the workshop from GitHub. Which command will it want to run, and will it ask you first?
  3. Send:
    Clone https://github.com/sunholo-data/claude-code-workshop into this folder, then tell me how to start the workshop.
  4. Claude shows you the command (git clone …) and asks before running it. Read it, then allow it.

    The big button may say Always allow: that saves a rule, so this command never asks again in this folder. Look at the arrow beside it before choosing. Which you pick is your first trust decision of the day. Reading approvals is the habit the whole day builds.

    You should see: Cloning into 'claude-code-workshop'…, then a short answer: start a new session on the workshop folder. Asking for the one thing you want next, rather than "what's in it?", gets a short answer.

  5. Start a new session yourself: + New at the top left. Click the folder button under the message box: it still says claude-test. Choose Open folder…, go into claude-test, and pick claude-code-workshop. Set the mode to Manual. You should see: the folder button says claude-code-workshop.
  6. Predict: what would it mean to trust a folder you hadn't read?
  7. You'll see This workspace isn't trusted. A folder you downloaded can carry its own Claude settings, so Claude asks before using them. Send:
    start the workshop

    and choose Trust workspace: that's what lets the course's guide, rules and settings load. If the banner shows but the question never comes, quit Claude Desktop and open it again, then go back to this session.

    This folder also lists one MCP server, google-developer-knowledge, in its .mcp.json. If you are asked whether to use it, allow it: you'll use it in block 6, and it does nothing until you add a key there. A notice that GOOGLE_DK_API_KEY is missing is expected for the same reason; ignore it until then.

  8. The guide reads the course and offers you somewhere to start. The first time, it asks to create progress.md, your own record of what you've done. Allow it. You should see: a short list of where you can start, and progress.md in the folder.

If git isn't working yet

On the GitHub page, click the green Code button, then Download ZIP. Unzip it and select the unzipped folder in step 5. Block 2 works the same way up to trust-ladder, which needs git, and so does everything after it. Before then, get git working (git-installed), redo step 3, and ask Claude to copy your progress.md across to the new folder.

Proof
The guide answered start the workshop from a session opened on the workshop folder, and progress.md exists in that folder.
Watch for
  • "Claude is inside GitHub." Claude works on files on your laptop. GitHub is where the shared copy lives; cloning brings a copy down.
  • "One session can see everything." A session sees the folder you chose. That's why step 5 opens a new session on the workshop folder, rather than carrying on in claude-test.

Permissions and reviewing changes

I can pick a permission mode, read a diff, and reject a change I don't want.

Do

Where: a session on the claude-code-workshop folder, in Manual.

  1. Check the mode button under the message box says Manual.
  2. Predict: you'll send the deliberately vague prompt below. What will "tidy" mean to Claude? Which lines will it touch?
    Tidy up samples/tagging-plan.md.
  3. Send it. Read the diff before deciding: red is removed, green is added. Look for anything you didn't ask for, such as a reworded open question or a changed date. You should see: a proposed change and a request to save it. Nothing to review because it saved straight away? The mode isn't Manual: set it and ask again. Claude lists a few options and asks which you want, instead of editing? That's a fair answer to a vague request: pick one, and it will propose the change.
  4. Click Reject on at least one change, and say out loud why. You should see: Claude asking how to proceed. Tell it precisely what you do want, such as:
    Only fix the formatting of the table. Don't change any wording or dates.

    and accept that.

  5. Switch the mode to Accept edits and send:
    In samples/tagging-plan.md, change "Last reviewed" to today's date.

    You should see: the file saved without a prompt, and a +N -N indicator. Click it to review the change after the fact.

  6. Put samples/ back as it was, so later exercises start from the original files. Switch back to Manual and send:
    Put the samples folder back exactly as it was in the last commit, with git restore samples/.

    You should see: a request to run git restore samples/ (it's an ask rule: approve it), then no changes in samples/. Check with !git status.

Proof
One change rejected and re-asked, with the reason said aloud.
Watch for
  • "Accepting is a formality." The diff is the one moment you see exactly what will change. Reading it is the job.
  • "Rejecting means starting again." Claude keeps the conversation and asks what you want instead.

Plan before acting

I can use Plan mode to agree an approach before anything is changed.

  3. Send it. You should see: Claude reading the file, then a plan. No edit and no save prompt: Plan changes nothing.

A plan you changed before approving it, and the file that followed it.

Trust is earned per action

I can say which of Claude's actions I approve every time, which I let through, and which it may never do, and why each sits where it does.

Do

Where: first a session on the claude-code-workshop folder, in Manual, to build three copies. Then one + New session on each copy, which you open yourself: ladder-manual in Manual, ladder-accept in Accept edits, ladder-auto in Auto. The copies have no rules of their own yet, which is the point.

  1. Check git knows who you are. Send:
    !git config user.email

    You should see: your email. Nothing? Git won't ask you later: a commit either stops with "Author identity unknown" or, on a Mac, goes through under a made-up name from your laptop's name. Set it now:

    Set my git name to <your name> and email to <the email on your GitHub account>, for every repository.
  2. Build the three copies, each with its own first commit and its own place to push to. In the workshop session:
    Next to this workshop folder, not inside it, make three folders: ladder-manual, ladder-accept and ladder-auto. Copy the files in samples/ into each one, not the samples folder itself. Make each a git repository and commit those files. Then, also next to this folder, make three empty repositories with git init --bare: ladder-manual-remote.git, ladder-accept-remote.git and ladder-auto-remote.git. Add each one to its folder as the remote called origin.

    You should see: several approval prompts (approve them: this session's prompts don't count), then three folders and three .git repositories next to claude-code-workshop. Check with !ls ... Nothing goes to GitHub: each copy pushes only to a folder on your laptop.

  3. Predict: you'll send the task below once in each copy. How many times will Claude stop and ask in Manual? In Accept edits? In Auto? Write your three numbers down.
    Sort the files in this folder into folders by type, write a short README listing them, and commit.
  4. + New, open ladder-manual, set the mode to Manual, and send the task from step 3. Count every approval prompt. You should see: a prompt for most steps: making folders, moving files, writing the README, committing. If it asks whether you trust the folder, say yes; that one doesn't count.
  5. + New, open ladder-accept, set Accept edits, send the task, count.
  6. + New, open ladder-auto, set Auto, send the task, count. No Auto in the mode selector? Your plan or organisation hasn't turned it on. Do 4 and 5, and skip step 7.
  7. Still in the ladder-auto session, guess first: will it ask, try, or refuse? Then:
    Now push this to origin.

    You should see: either a push to ladder-auto-remote.git or a prompt. With no rules, whether Auto stops is a background check's call, not yours. In block 3 you add an ask rule for git push, and from then on it stops for you even in Auto. That is a ceiling: publishing stays at proposing, permanently.

  8. Go back to the ladder-manual session and ask for one more small change:
    Add one line to the README saying when these files were sorted, and commit it.

    When it asks to run git commit, choose Always allow. Then ask for another line and a commit. You should see: no prompt for the commit this time. You've promoted one action from proposing to automated, on the evidence that you approved it each time without changing anything. The rule is saved in this folder only.

Proof
Your three predicted and three actual prompt counts, and what Auto did when you asked it to push.
Watch for
  • "Auto mode means I've stopped checking." You've stopped checking the routine. The actions you've marked as ask still stop for you, every time.
  • "Trust is a setting for the whole session." It's per action. The same session can commit freely and still ask before every push.

Choosing a model

I can choose a model for a task, and say what I trade between quality, speed and plan usage.

Do

Where: a session on the claude-code-workshop folder, in Manual.

  1. Open the model menu at the bottom right, under the message box, and note which models you can choose and which one is selected.

Sessions and context

I know when to start a fresh session, and why long sessions get worse.

Do

Where: a session on the claude-code-workshop folder, in Manual, then two + New sessions on the same folder.

  1. Look back at one of your earlier sessions today, in the sidebar. How many different things did you ask for in it?
  2. Predict: you start a new session and ask "carry on with the tagging plan". What will Claude know about what you did before: nothing, the files, or your earlier conversation?
  3. + New, open claude-code-workshop, Manual, and send exactly:
    carry on with the tagging plan

    You should see: Claude reading files to work out what you mean, or asking. It has the folder, its CLAUDE.md, and any notes it saved for itself, but not your earlier conversation.

  4. Now write a one-paragraph brief instead: what the task is, which files matter (with @), what is already done, and what "done" looks like. For example:
    I'm adding a section on the search event to @samples/tagging-plan.md. Nothing is written yet. It should say what we record, what we must not record (email addresses typed into search), and who signs it off, in under ten lines. Show me a plan first.

    + New again, same folder, and send your brief.

  5. Know the other tool: typing /compact asks Claude to summarise the current session now and keep going, which frees room without starting over.
Proof
A task restarted in a new session from your one-paragraph brief.
Watch for
  • "It remembers yesterday." A new session doesn't have your earlier conversation. It starts with the folder, any standing instructions (that's the next tier, CLAUDE.md), and its own auto memory: short notes Claude chose to keep from earlier sessions on this folder. Not what you said.
  • "Longer conversations give it more to go on." Past a point they give it more to get confused by.

CLAUDE.md — standing instructions

I can write a CLAUDE.md and watch it change what Claude does.

Do

Where: a session on the claude-code-workshop folder, in Manual, then a + New session on the same folder.

  1. Before. Send:
    What happened to newsletter signups in samples/daily-sessions.csv? Give the dates.

    Note how it writes dates, and whether it says what it read.

  2. Create CLAUDE.local.md yourself, not by asking Claude: if Claude wrote it, the rule would already be in this conversation and step 4 would prove nothing.
    • Mac: open TextEdit, File → New, then Format → Make Plain Text.
    • Windows: open Notepad. Paste this one line:
    - Write dates as "15 Sept 2026", never 2026-09-15. End every answer with "Read:" and the files you read.

    Save it in the claude-code-workshop folder as CLAUDE.local.md (on a Mac, untick If no extension is provided, use ".txt"; in Notepad, set Save as type to All files).

    You should see: CLAUDE.local.md next to CLAUDE.md in the folder, not CLAUDE.local.md.txt.

  3. Predict: you ask the same question again in the same session. Will the rule apply?
  4. Try it: send the step 1 prompt again in this session. Then + New, open claude-code-workshop, Manual, and send it once more. You should see: most likely, the old style in the first session and the new one in the new session: the file is read when a session starts. No change in the new session? Check the file's name and that it's in the workshop folder itself.
  5. Make the rule worse on purpose. In your editor, replace the line with "be clear about dates", save, start another + New session, ask again, and see what survives.
  6. Don't commit CLAUDE.local.md; it's yours, and git already ignores it. The rule now applies to every later session on this folder, the guide's included. Delete the line when you're done with it, or keep it if you like answers that say what they read.
Proof
The same request answered before and after one rule, with the difference visible, and you can say which rule caused it.
Watch for
  • "I told it once, so it knows." A message lasts one session. A line in CLAUDE.md lasts every session.
  • "It picks up the change immediately." The file is read when a session starts; that's why you needed a new one.

Team conventions and data handling

I can say what may and may not be given to a model, and where that rule is written down.

Do

Where: the whole group together, with the facilitator's shared document open (they send the link). Then each person in a session on the claude-code-workshop folder, in Manual.

  1. Read your group's data rule, word for word:
    Show me the data_policy line in overlay/overlay.yaml and everything in overlay/CLAUDE.md, word for word. Don't summarise.

    You should see: the rule, quoted. "There's no overlay folder"? Ask the facilitator for the rule in writing before going on.

  2. Predict: on your own, before anyone talks, write down one kind of material you think is fine to give Claude and one you think isn't. Then compare as a group. Where did you disagree?
  3. Together, in the shared document, write under these headings, in this order:
    • Data handling: the group's rule, pasted word for word; what's allowed; what isn't; who to ask when unsure (a name).
    • Our lines: empty for now.
  4. Each person adds one line of their own under Our lines: a habit, a check, a naming rule, anything you'd want a colleague's Claude to follow.
  5. When everyone's line is in, select the whole document, copy it, and paste it after this prompt:
    Save the text below as CONVENTIONS.md in this folder, exactly as written. Don't commit it.

    You should see: a request to create CONVENTIONS.md (approve). It stays out of your commits: in the follow-up it moves into the team's own repository.

  6. Point your own sessions at it. This goes in your personal file, not the shared CLAUDE.md:
    Add the line "Follow CONVENTIONS.md." to CLAUDE.local.md in this folder. Create the file if it doesn't exist.
  7. + New for a fresh session on the same folder, and ask:
    What may and may not you do with client material in this folder, and where is that written?

    You should see: the rule from CONVENTIONS.md, with the file named. If it answers from general knowledge instead, check step 6 saved, and that this is a new session.

Proof
Your line in the team's conventions file, and you can say where the data rule is written.
Watch for
  • "Data rules are IT's problem." The choice of what goes into a session is made by whoever types it, every time.
  • "If Claude can open a file, I'm allowed to give it." Access is not permission. The rule decides, not the folder.

Your rules — allow, ask, deny

I can write the settings that let routine actions through, always stop for the risky ones, and block the ones that must never happen.

Do

Where: first a session on the claude-code-workshop folder, in Manual, to build a folder called rules-practice next to it. Then a + New session on rules-practice, in Auto, and later Manual.

  1. Read settings/README.md: one line per rule, saying which rung it puts the action on and why.
  2. Predict: with these rules, which of these will just happen, which will ask, and which will be refused? Commit a change. Push it. Delete a file. Read a file called .env.

Team skills in every folder

I can package the team's skills as a plugin from our own marketplace, so they work in any folder, not only the skills repo.

Do

Where: a session on the team skills repository's folder, in Manual, and that session's terminal pane (Ctrl and the backtick key). Then a + New session on a different folder, such as claude-code-workshop.

  1. Install the command line, once, in the terminal pane. On a Mac:
    curl -fsSL https://claude.ai/install.sh | bash

    On Windows, in PowerShell: irm https://claude.ai/install.ps1 | iex. Then close the terminal pane, open it again, and run claude --version.

    You should see: a version number. command not found? Follow what the installer printed about adding it to your PATH, then open the pane again. Source: code.claude.com/docs/en/quickstart.

  2. Predict: you open a session on a client folder and ask for something a team skill does. Will it be used? Why not?
  3. Reorganise the repository on a branch, because moving the skills out of .claude/skills/ takes them away from everyone's sessions on this repository until they install the plugin:
    Make a branch called plugin-marketplace. Following code.claude.com/docs/en/plugin-marketplaces, reorganise this repository as a marketplace with one plugin called <plugin>: each skill under plugins/<plugin>/skills/<skill>/SKILL.md; plugins/<plugin>/.claude-plugin/plugin.json with the plugin's name and no version field; and .claude-plugin/marketplace.json at the root with a name, an owner, and one entry named <plugin> whose source is "./plugins/<plugin>". Commit.

    Leaving out version means each new commit is a new version. If you set one, you must raise it on every change, or colleagues keep the old copy.

  4. Check it, in the terminal pane:
    claude plugin validate .

    You should see: Validation passed. Then push the branch and open a pull request, as in share-skill-pr; a reviewer merges it.

  5. Once it's merged, add the marketplace and install the plugin for yourself, in every folder, in the terminal pane:
    claude plugin marketplace add <org>/<repo>
    claude plugin install <plugin>@<marketplace> --scope user

    You should see: the plugin installed at user scope. Project or local scope would install it for this folder only, and step 6 would fail.

  6. + New on a different folder, such as claude-code-workshop, and run a team skill as /<plugin>:<skill>.
  7. Find out how a colleague gets your next change, and write it in the repository's README. A team's own marketplace doesn't auto-update by default.
Proof
A team skill run as /<plugin>:<skill> from a session on a different folder.
Watch for
  • "A plugin is a different kind of skill." It's the same SKILL.md files, packaged so they travel.
  • "Once installed, everyone always has the latest." Installs are copies. Check how and when updates reach people before you rely on it.
