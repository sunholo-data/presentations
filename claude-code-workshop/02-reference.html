Tier 0 · setup · core: everyone, today

Claude Desktop, Code tab

I can open a folder in the Code tab and get Claude to create a file in it.

Do
  1. Download Claude Desktop from claude.com/download, install it, and sign in.
  2. Click the Code button (</>) at the top left. If it asks you to upgrade, your plan doesn't include it; tell the facilitator before the day.
  3. Make an empty folder somewhere easy to find, for example claude-test in your Documents.
  4. Click + New. In the bar under the message box, choose This computer, then the folder button and Open folder…, and pick claude-test.
  5. In the same bar, the mode button says Auto: that's the default. Click it and choose Manual. Leave Bypass permissions alone.
  6. Predict: you type "Create a file called hello.txt that says hello". Will the file just appear? Will Claude ask you first? Where on your computer will it go?
  7. Send it. Accept the change when it asks. Then open the folder in Finder or File Explorer and look.
Proof
hello.txt exists in your test folder, and you opened it yourself.
Watch for
  • "It's the same as the chat tab." The Chat tab has no access to your files; the Code tab works in the folder you chose, and only there unless you allow more.
  • "I need to install developer tools first." Not for this. Git comes next, and only because the later lessons use it.

Needs: nothing

Tier 0 · setup · core: everyone, today

Git and a GitHub account

I have git installed and a GitHub account I can sign in to.

Do
  1. Predict: is git already on your computer? Most Macs have it, or offer to fetch it; most Windows PCs don't.
  2. Open a session in the Code tab (any folder, claude-test is fine). In the message box, type !git --version and send it. The ! means run this myself: the command runs straight away, without Claude and without asking, and the result appears in the conversation.
  3. If it prints a version number, you're done with this step. If not:
    • Mac: git comes with Apple's developer tools. Asking for git when they're missing makes macOS offer to install them in a pop-up: click Install and wait a few minutes. No pop-up? Send !xcode-select --install.
    • Windows: install Git for Windows from git-scm.com/downloads/win, accepting the defaults. Restart Claude Desktop afterwards so it finds git.
  4. Send !git --version again.
  5. If you don't have a GitHub account, make one at github.com/signup. Use the email you'll use for work, and turn on two-factor sign-in when it offers.
  6. Send your GitHub username (not your password) to the facilitator.

You could also ask Claude to check for git and explain what it finds. The difference: with ! you run the command; without it, Claude decides what to run and asks you first.

Proof
!git --version in the Code tab prints a version, and the facilitator has your GitHub username.
Watch for
  • "Git and GitHub are the same thing." Git is the tool on your laptop and works with no account at all. GitHub is a website that stores copies of git repositories so people can share them.
  • "Commands need a terminal." A ! in the message box runs one for you, and Claude can see the result. Most of the day you will ask Claude to run commands and read them, not type them.

Tier 0 · setup · core: everyone, today

Get the workshop

I can have Claude clone a repository from GitHub, and open a session on it.

Do
  1. In the Code tab, open a session on your claude-test folder (the one from install). Keep the mode on Manual.
  2. Predict: you ask Claude to copy the workshop from GitHub. Which command will it want to run, and will it ask you first?
  3. Send:
    Clone https://github.com/sunholo-data/claude-code-workshop into this folder, then tell me how to start the workshop.
  4. Claude shows you the command (git clone …) and asks before running it. Read it, then allow it. The big button may say Always allow: that saves a rule, so this command never asks again in this folder. Look at the arrow beside it before choosing. Which you pick is your first trust decision of the day. This is the first of many approvals; reading them is the habit the whole day builds. Then it tells you the next step, from the README: a new session on the workshop folder. Asking for the one thing you want next, rather than "what's in it?", gets a short answer.
  5. Start a new session (+ New at the top left). Click the folder button under the message box: it still says claude-test. Choose Open folder…, go into claude-test, and pick claude-code-workshop. Check the button now says claude-code-workshop.
  6. You'll see This workspace isn't trusted. A folder you downloaded can carry its own Claude settings, so Claude asks before using them. Type start the workshop, send it, and choose Trust workspace: that's what lets the course's guide, rules and settings load. If the banner shows but the question never comes, quit Claude Desktop and open it again, then go back to this session. Predict first: what would it mean to trust a folder you hadn't read?
  7. The guide reads the course and offers you somewhere to start. The first time, it asks to create progress.md, your own record of what you've done. Allow it.

If git isn't working yet

On the GitHub page, click the green Code button, then Download ZIP. Unzip it and select the unzipped folder in step 5. Everything up to the Git lessons works the same way. Once git works, redo step 3, and ask Claude to copy your progress.md across to the new folder.

Proof
The guide answered start the workshop from a session opened on the workshop folder, and progress.md exists in that folder.
Watch for
  • "Claude is inside GitHub." Claude works on files on your laptop. GitHub is where the shared copy lives; cloning brings a copy down.
  • "One session can see everything." A session sees the folder you chose. That's why step 5 opens a new session on the workshop folder, rather than carrying on in claude-test.

Chat versus agent

I can explain what changes when the AI reads and writes files and runs commands, instead of me pasting text in and out.

Do
  1. Open this workshop folder in the Code tab (+ New, This computer, then the folder button and Open folder…). Keep the mode on Manual.
  2. Open samples/tagging-plan.md yourself and skim it. It is a made-up plan for a made-up shop.
  3. Predict: you ask "In samples/tagging-plan.md, mark the search event as Live and add a row to the change log for today." What will Claude do first: answer from memory, or read the file? What will it ask you before saving anything?
  4. Send it. Watch the steps it shows: reading, then proposing a change. Accept it.
  5. Open the file again yourself. Is the change exactly what you asked for, and nothing else?
  6. Compare: how would you have done this in a chat window? Count the copy-and-paste steps.
Proof
Claude edited samples/tagging-plan.md, and you opened it afterwards and said what changed.
Watch for
  • "It will reply with the new text for me to paste." It changes the file on disk. The reply is a report of what it did, which is why you check the file and not only the reply.
  • "It already knows what's in my files." It reads them when it needs to, in this session. You can watch it do so.

Permissions and reviewing changes

I can pick a permission mode, read a diff, and reject a change I don't want.

Do
  1. Set the mode to Manual.
  2. Ask: "Tidy up samples/tagging-plan.md." That is deliberately vague.
  3. Predict: what will "tidy" mean to Claude? Which lines will it touch?
  4. Read the diff it shows before deciding: red is removed, green is added. Look for anything you didn't ask for, such as a reworded open question or a changed date.
  5. Click Reject on at least one change, and say out loud why.
  6. Claude will ask how to proceed. Tell it precisely what you do want, and accept that.
  7. Switch to Accept edits, ask for one more small change, then click the +N -N indicator that appears to review it after the fact.
Proof
One change rejected and re-asked, with the reason said aloud.
Watch for
  • "Accepting is a formality." The diff is the one moment you see exactly what will change. Reading it is the job.
  • "Rejecting means starting again." Claude keeps the conversation and asks what you want instead.

Plan before acting

I can use Plan mode to agree an approach before anything is changed.

Do
  1. Set the mode to Plan.
  2. Ask: "Add a section to samples/tagging-plan.md describing how we'd track the search event, including what must not be recorded."
  3. Predict: what will the plan contain? Will it pick up the open question about email addresses in search terms on its own?

A plan you changed before approving it, and the file that followed it.

Trust is earned per action

I can say which of Claude's actions I approve every time, which I let through, and which it may never do, and why each sits where it does.

Do
  1. Ask Claude to copy samples/ to a new folder called ladder-practice next to the workshop folder (not inside it), make it a git repository, and then open a + New session on it. It has no rules yet, which is the point. You'll run the same task three times, so each run needs a fresh copy.
  2. The task, each time: "Sort the files in ladder-practice into folders by type, write a short README listing them, and commit." The first commit on a new laptop may stop to ask for your name and email: that's git, not Claude. Give them once and it won't ask again.
  3. Predict: how many times will Claude stop and ask in Manual? In Accept edits? In Auto? Write your three numbers down.
  4. Run it in Manual and count the prompts. Then reset the copy, switch to Accept edits, and run it again. Then Auto. (If Auto isn't in the mode selector, your plan or organisation hasn't enabled it; do the first two.)
  5. Still in Auto, ask: "Now push this to GitHub." Predict first: will it ask, try, or explain? This copy has no GitHub repository yet (that's block 4), and with no rules, whether Auto stops is a background check's call, not yours. In block 3 you add an ask rule for git push, and from then on it stops for you even in Auto. That is a ceiling: publishing stays at proposing, permanently.
  6. In Manual mode, find a command you've approved several times without changing anything. Choose Always allow. You've just promoted one action from proposing to automated, on the evidence of how often you changed nothing.
Proof
Your three predicted and three actual prompt counts, and what Auto did when you asked it to push.
Watch for
  • "Auto mode means I've stopped checking." You've stopped checking the routine. The actions you've marked as ask still stop for you, every time.
  • "Trust is a setting for the whole session." It's per action. The same session can commit freely and still ask before every push.

Choosing a model

I can choose a model for a task, and say what I trade between quality, speed and plan usage.

Do
  1. Open the model dropdown and note which models you can choose and which one is selected.
  2. Predict: you'll ask two models the same thing. Which will be faster? Which answer will you prefer, and will you be able to tell them apart?
  3. On one model, ask: "Read samples/daily-sessions.csv and give me three bullet points on what happened in September."
  4. Start a new session (+ New session), choose a different model, and ask exactly the same thing.
  5. Compare: speed, accuracy (check one number against the CSV), and whether either noticed the signups dropping to zero.
Proof
The same task on two models, and one sentence on the difference you saw.
Watch for
  • "Always use the biggest model." It costs more of your allowance and is slower; for a small, well-described task it often adds nothing.
  • "The model is the only thing that matters." A clear request and the right files usually change the answer more than the model does.

CLAUDE.md — standing instructions

I can write a CLAUDE.md and watch it change what Claude does.

Do
  1. Before. In a session on this folder, ask: "What happened to newsletter signups in samples/daily-sessions.csv? Give the dates." Note how it writes dates, and whether it says what it read.

Team conventions and data handling

I can say what may and may not be given to a model, and where that rule is written down.

Do
  1. If this folder has overlay/, read overlay/CLAUDE.md and the data_policy line in overlay/overlay.yaml. That is your group's data rule, and it wins. If there's no overlay, ask the facilitator for the rule in writing.
  2. Predict: before anyone writes anything, each person writes down privately one kind of material they think is fine to give Claude and one they think isn't. Compare as a group. Where did you disagree?
  3. Together, write the conventions in the shared document the facilitator opens for the group. Data handling first: what's allowed, what isn't, and who to ask when unsure. Quote the group's data rule rather than paraphrasing it. Then ask Claude to save a copy as CONVENTIONS.md in this workshop folder. In the follow-up it moves into the team's own repository, where everyone's projects can point to it.
  4. Then each person adds one line of their own: a habit, a check, a naming rule, anything you'd want a colleague's Claude to follow.
  5. Add one line to your CLAUDE.md (or CLAUDE.local.md): "Follow CONVENTIONS.md." Ask Claude, in a new session, what it may and may not do with client material. Does the answer match?
Proof
Your line in the team's conventions file, and you can say where the data rule is written.
Watch for
  • "Data rules are IT's problem." The choice of what goes into a session is made by whoever types it, every time.
  • "If Claude can open a file, I'm allowed to give it." Access is not permission. The rule decides, not the folder.

Your rules — allow, ask, deny

I can write the settings that let routine actions through, always stop for the risky ones, and block the ones that must never happen.

Do
  1. Read settings/README.md: one line per rule, saying which rung it puts the action on and why.
  2. Predict: with these rules, which of these will just happen, which will ask, and which will be refused? Commit a change. Push it. Delete a file. Read a file called .env.
  3. In your ladder-practice repository, ask Claude to copy the permissions block from settings/starter.json into .claude/settings.json. Read the result before you approve it.
  4. Start a new session there, in Auto. Ask for each of the four actions in step 2 (make a .env file with one made-up line first). Compare with your prediction.
  5. Open .claude/settings.local.json and find the rule you promoted in the trust-ladder node. Decide whether it belongs in the team's file or only in yours.
  6. Add one rule of your own for something in your real work that should always ask, and say why.
Proof
The settings file in use, one rule you promoted yourself, and the push or the delete you saw it stop.
Watch for
  • "Writing 'never push without asking' in CLAUDE.md does the same job." CLAUDE.md shapes what Claude tries to do. Permission rules are enforced by Claude Code whatever the model decides.
  • "A narrow allow can make an exception to a broad ask or deny." It can't. Deny and ask are checked first, which is why git checkout asks even though moving between branches is safe: use git switch for that.

What else settings can do

I can choose which settings file a setting belongs in (the team's, mine for this project, or mine everywhere) and check that it took effect.

Do
  1. Predict: which file does each of these belong in? Every new folder starts in Manual. Your API key. Claude answers in French. Claude may read the team's shared folder of briefs.
  2. Ask Claude which file each one belongs in, and why. Compare with your prediction. The key is the one with a fixed answer: settings.local.json, as in add-mcp.

One setting you added, the file you chose and why, and a new session where you saw it work.

Tier 3 · git · core: everyone, today

Git as undo

I can ask Claude to commit my work, see what changed, and go back.

Do
  1. Ask Claude: "Copy the samples folder to a new folder called workshop-practice next to this one, and make it a git repository with a first commit." Read each command before approving. The first commit may stop to ask for your name and email; that is git, not Claude.
  2. Start a + New session with workshop-practice as the folder.
  3. Ask for two small changes to tagging-plan.md, committing after each: "commit this with a message saying what changed."
  4. Ask: "Show me the history, and what changed in the last commit."
  5. Predict: you ask "undo the last commit's change". What happens to the file? What happens to the history: is the commit deleted, or is a new one added?
  6. Try it. Open the file, then ask for the history again.
Proof
At least three commits in the log, one of which undoes an earlier change.
Watch for
  • "Undo means the mistake is erased." The safe way, a revert, adds a new commit that reverses the old one. The history keeps both, which is the point.
  • "Git saves automatically." Only when you commit. Changes since the last commit can't be recovered by git.

Tier 3 · git · core: everyone, today

Clone, branch, push

I can clone a repository, work on a branch, and push it.

Do
  1. You already cloned this workshop repository. That clone is today's practice repository: work in a session on it.
  2. Sign-in check. Ask Claude: "Can git push to GitHub from here? Don't push anything; just check how it would sign in." On Windows, Git for Windows opens a browser window when it needs you. On a Mac it usually can't ask: install GitHub CLI from cli.github.com, then in the terminal pane (Ctrl+) type gh auth login, choose the browser option, and afterwards gh auth setup-git. Use the terminal pane, not !: sign-in asks you questions, and anything run with !` lands in the conversation. Never paste a password or token into the chat.
  3. Ask: "Make a branch called practice/<your-github-username>."
  4. Make one small change (a line in your own notes/<your-github-username>.md) and ask Claude to commit it.
  5. Predict: you ask Claude to push the branch. Will it ask you first? Will your change appear on the main branch on GitHub?
  6. Ask it to push. Then open the repository on GitHub, find the branch list, and open yours.
  7. Now try the thing you shouldn't be able to do: ask Claude to push your commit straight to main. Read what GitHub says back.

Not in a facilitated group? You won't have permission to push here. Ask Claude to fork the repository to your own GitHub account (gh repo fork --remote) and push your branch to the fork. That needs the GitHub CLI: on Windows too, install it from cli.github.com and sign in with gh auth login in the terminal pane first.

Proof
Your branch visible on GitHub, with your commit on it, and GitHub's refusal when you pushed to main.
Watch for
  • "Pushing changes everyone's copy." It adds your branch to GitHub. Nothing reaches the main branch until someone merges it, and nobody's laptop changes until they pull.
  • "Cloning is downloading." A download is a snapshot. A clone keeps the history and knows where it came from, so you can push back and pull updates.

Tier 4 · skills · core: everyone, today

Use someone else's skill

I can clone a repo that carries a skill and get the result its author intended, without knowing how.

Do
  1. In a session on any folder, ask Claude: "Clone https://github.com/sunholo-data/presentation-template into my Documents folder." Then start a + New session on the cloned folder. The skill only loads in a session opened on that folder.
  2. Open demo/presenter.html in your browser to see a finished deck. The arrow keys move between slides; the sun/moon button switches theme.
  3. Predict: you are going to ask for a deck without naming the skill. Will Claude use it anyway? Which files will it open first?
  4. Ask: "Build a 3-slide deck in my-deck/ about <something you know well>." Watch which files it reads before it writes anything.
  5. Run the check yourself by sending this with a ! in front, or ask Claude to run it:
    !node .claude/skills/presentation-slides/scripts/lint-slides.mjs my-deck/*.html

    No output means it passed. It needs Node: if node is not found, ask Claude to install it, or skip the lint and do step 6 carefully.

  6. Open your deck in the browser. Switch theme. Then make the window tall and narrow: does anything spill off the slide?
Proof
A three-slide deck in my-deck/, built with the presentation-slides skill, passing its lint, and the lint command you ran, with the deck's file names in it.
Watch for
  • "To use a skill I need to know how it works." You asked in your own words. The skill's description matched the request, and Claude did the rest.
  • "The lint passed, so my deck was checked." Run it with just the folder name, my-deck, instead of my-deck/*.html. It prints nothing and reports success, because it checked no files at all. A check that cannot fail tells you nothing.

Tier 4 · skills · stretch: if you finish early

How a skill is built

I can read a SKILL.md and say when it triggers, what it tells Claude, and what it carries with it.

Do
  1. In your presentation-template session from use-a-skill, open .claude/skills/presentation-slides/SKILL.md.
  2. Find the three parts. Copy out the description. List the files in resources/ and scripts/, and for each one find the sentence in the body that tells Claude when to use it.
  3. Predict: which of these will trigger the skill? "Make me some slides", "I need something to show on the screen on Thursday", "Turn these notes into something I can present." Write yes or no for each.
  4. Try each in a fresh session on the folder, so nothing carries over. Afterwards, ask "Which skill did you use, if any?"
  5. Pick a phrase you would really say that missed, or only just hit. Edit the description so it covers that phrase, without making it so broad that it fires on any request about a document.
  6. Start a new session and try your phrase again.
Proof
The skill's description rewritten so it triggers on a phrase you'd actually use, shown working in a new session.
Watch for
  • "Claude reads every skill all the time." It reads every description. The body loads only when the skill is used, which is why a folder can carry many skills, and why a vague description means a skill that never fires.
  • "The name is what makes it fire." The name is how you call it directly (/presentation-slides). Picking it unprompted is the description's job.

Tier 4 · skills · homework: before the follow-up

Write your own skill

I can turn something I do repeatedly into a skill that someone else could run.

Do
  1. Pick a task you do at least weekly and can describe in about five steps. Use material your group's data rule allows, or a made-up stand-in of the same shape.
  2. In a repository of your own (the practice repository from clone-branch is fine), do the task once with Claude. Note every time you had to correct it.
  3. Ask: "Turn what we just did into a project skill at .claude/skills/<short-name>/SKILL.md. Include the corrections I made." Read the result before accepting it.
  4. Check the description. Is it in the words you'd use when you need this, and does it say when the skill should not be used?
  5. If the output has a fixed format, put a template in resources/. If a step is mechanical, such as counting, renaming or reformatting, ask for a script in scripts/ instead of an instruction.
  6. Predict: a colleague opens this folder and asks for the task in their own words. What will they get, and at which step will they need to ask you something?
  7. Commit and push. Have a colleague clone the repository, start a new session on it, and ask for the task. Say nothing; watch.
  8. Fix what they stumbled on. It is usually the description, an input nobody told them to supply, or something only you knew.
Proof
A colleague runs your skill and gets the right result without asking you.
Watch for
  • "A skill is just a saved prompt." It is a prompt, a rule for when to use it, and the files it carries, kept in git so that changes to it are visible and reviewed.
  • "It works for me, so it works." What you know leaks in without you noticing. The colleague test is the only one that finds it.

Tier 4 · skills · core: everyone, today

Your skill, in everyone's copy

I can propose a change by pull request, and once it is merged, pull and see my work and everyone else's in my own copy.

Do
  1. Start from an up-to-date main: ask Claude to switch to main and pull.
  2. Ask for a branch named skill/<your-github-username>.
  3. Write one small skill in its own folder, .claude/skills/<your-github-username>-<skill-name>/SKILL.md (for example .claude/skills/mark-explain-diff/), and change nothing else. The folder name is what everyone will type after /, and your username keeps it from clashing with a colleague's. Ideas, all things you'd want today:
    • explain-diff: "explain what changed since my last commit, in plain English"
    • where-was-i: "summarise my progress.md in three lines"
    • check-before-push: "list what's about to be pushed, and anything that looks private" Give it a description that says when it should be used, in words someone else would type.
  4. Try it yourself in a new session (skills load when a session starts), then commit.
  5. Predict: after you push and open a pull request, will your skill appear in your neighbour's Code tab? When will it?
  6. Push the branch, and ask Claude to open a pull request (or open it on GitHub: the yellow Compare & pull request banner). Say in one line what the skill does.
  7. Wait for the facilitator to merge. You can't merge it yourself: main only changes through a reviewed pull request. Look at the PR on GitHub while you wait.
  8. When everything is merged, ask Claude to switch to main and pull. Start a new session, type /, and find your skill and the others. Run one written by someone else.
Proof
After the merge and a pull, your skill and a colleague's both appear when you type /, and you ran theirs.
Watch for
  • "Merged means everyone has it." Merged means it's on GitHub's main. Nobody's laptop changes until they pull.
  • "I pushed, so it's in main." You pushed a branch. Someone else decides whether it joins main.

Connectors and MCP

I can explain the difference between pasting an export and connecting the source, and what each sends to the model.

Do
  1. Find the Connectors list in the panel on the right of the Code tab. Which are on? Each one's tools are available to Claude in this session.
  2. Choose a question you could answer from a source your group's rules allow (a calendar or a shared drive folder are typical). Check the rule before you start.
  3. Export route: put an export or copy of the data in the folder and ask the question with @ on that file. Write down exactly what you gave it.
  4. Predict: you ask the same question in a new session, with the connector on and no file. What will Claude fetch? More than your export, or less?
  5. Ask. Expand the tool calls: which tool, with what search terms, and what came back.
  6. Say the data path out loud: where the data came from, which tool fetched it, whose account it ran as, and where it went next.
Proof
A question answered from a connected source, with the data path said aloud.
Watch for
  • "Connecting is safer, because nothing is copied." What the tool returns goes into the conversation just as a paste does, and it may fetch more than you would have exported.
  • "A connector can see everything." It acts as you, so it reaches what your account reaches. No more, but no less either.

Tier 5 · connect · core: everyone, today

Add a remote MCP server

I can add a hosted MCP server to a project with an API key, and use its tools.

Do
  1. Ask Claude: "If .claude/settings.local.json doesn't exist, create it with an env entry GOOGLE_DK_API_KEY set to PASTE-KEY-HERE. If it does exist, don't touch it: tell me what to add." Claude can see whether the file is there but isn't allowed to read it, which is why it asks you to edit an existing one. Don't paste the key into the chat: anything in the chat is sent to the model.
  2. Open that file yourself and put your key in place of PASTE-KEY-HERE. If the file was already there, add the env part Claude gave you, keeping what's in it. In Finder, the .claude folder is hidden: press ⌘⇧. (Command, Shift, full stop) to show it. Save.
  3. Check it can't reach GitHub: send !git check-ignore -v .claude/settings.local.json. It names the .gitignore line that keeps the file private. Claude itself can't read the file: the repo's settings deny it, so the key never enters the chat.
  4. Start a new session so the server loads. If it asks whether to use this project's MCP server, say yes. /mcp lists the servers and whether they connected.
  5. Predict: ask "How do I add a custom dimension to a GA4 Data API report?" What will Claude do differently now that the server is there?
  6. Ask it. Look for a call to search_documents or answer_query.
Proof
An answer where Claude called one of those tools, and you can say which, and what it sent to Google.
Watch for
  • "Claude now knows the docs." It doesn't; it searches them each time, and only when it decides to.
  • "The key is a password for my account." It identifies a project, not a person. Anyone holding it can spend that project's quota, which is why it is restricted and why it is not committed.

Tier 5 · connect · homework: before the follow-up

Make your own API key

I can create a restricted API key in my own Google Cloud project and swap it in for the one I was lent.

Do
  1. Predict: when you swap your own key in, what will change for Claude, and what for you?

In the browser (Cloud console)

  1. Open console.cloud.google.com and choose the project at the top (or New project).
  2. APIs & Services → Library, search for Developer Knowledge API, click Enable.
  3. APIs & Services → Credentials → Create credentials → API key. Copy the key it shows.
  4. Click the new key, then under API restrictions choose Restrict key, tick Developer Knowledge API, and Save. Name it something you'll recognise later.
  5. Open .claude/settings.local.json yourself and replace the lent key with yours (never paste a key into the chat). Start a new session and check /mcp.

Or from the command line

Run these in the terminal pane (Ctrl+), after signing in there with gcloud auth login`.

gcloud services enable developerknowledge.googleapis.com --project=PROJECT_ID
gcloud services api-keys create --project=PROJECT_ID --display-name="Developer Knowledge"
gcloud services api-keys update KEY_NAME --api-target=service=developerknowledge.googleapis.com

create prints a keyString (the key) and a name (use it as KEY_NAME).

Proof
The server answers with your own key in settings.local.json in place of the lent one.
Watch for
  • "A new key means Claude can do more." Nothing changes for Claude: the same server, the same tools. What changes is who the use is billed to and who can switch it off: you.
  • "An unrestricted key is simpler." It is, for anyone who finds it: restricted to one API, a leaked key can do one thing.

GA4 data through BigQuery

I can connect Claude to Google's BigQuery server, query a GA4 export read-only, and say which data I was allowed to reach and why.

Do
  1. In claude.ai, open Settings → Connectors → Add custom connector. Name it BigQuery, set the URL to https://bigquery.googleapis.com/mcp, open Advanced settings, and paste the Client ID and secret. Click Add.
  2. Click Connect. Google asks you to sign in: choose the account your facilitator named. "Google hasn't verified this app" is expected for a practice setup; choose Continue, then allow BigQuery access.
  3. Quit the Desktop app and open it again. It reads your connectors when it starts, so one you added while it was open isn't there yet.
  4. Start a new Code tab session on your practice folder. Check that BigQuery is in the Connectors list on the right.
  5. Predict: ask "Using the BigQuery connector, what were the top five events in the GA4 sample in January 2021, and how many users triggered each?" Which tool will Claude use? Roughly how many page views?
  6. Run it. The tool calls are labelled BigQuery: …; open one and read the SQL before you read the answer. Is it counting what you asked?
  7. Ask a question you'd ask of a real client, for example where people drop out between viewing an item and adding it to the cart. Check one number yourself in the SQL.
  8. Ask Claude to list the datasets it can see. Is anything there you shouldn't be able to reach?
Proof
A query result from the GA4 sample through the connector, and one sentence on what left Google to produce it.
Watch for
  • "The export is the same as the GA4 reports." It's raw events. Totals won't match the GA4 screens exactly, and a property only exports from the day the link was set up.
  • "Connected means it can see all our data." It sees only the datasets your account was granted. Adding a client's export later is one grant, made after the team's data decision.

Tier 6 · share · core: everyone, today

One real task, end to end

I can take a real piece of my own work from request to checked result in the new mode.

Do
  1. Make a folder for the task and make it a git repository (ask Claude). Put in only the files the task needs and the rules allow.
  2. Write your request as a short brief: what you want, which files (@), and what "done" looks like. Use Plan mode if it has more than a couple of steps.
  3. Predict: before you send it, write one line on what you expect Claude to do, and one on where you think it will go wrong.
  4. Run it. Commit when something works. Reject or revert what doesn't.
  5. Check it against something you trust: open the files, recount a number, compare with the original, or ask Claude to show its evidence and check that yourself.
  6. Prepare three sentences for the room: what you asked, what it did, how you checked it. Include where it went wrong, if it did; that's the most useful part for everyone else.
Proof
Shown to the room: what you asked, what it did, and how you checked it.
Watch for
  • "If it finished without errors, it's right." Finishing is not the same as being correct. The check is your part of the job.
  • "Real work needs real data." Often the shape of the data is enough to build and test the method; the real run can wait for what the rules allow.

A review before anything is shared

I can explain why the team's main branch only changes through a reviewed pull request, and who reviews.

Do
  1. Predict: if you push a change straight to main, who sees it, and when?
  2. In the team repository on GitHub, open Settings → Rules (or Branches on some plans) and look at what protects main. If nothing does, ask whoever owns the repository to add a rule: require a pull request before merging, with at least one approval.
  3. Add a CODEOWNERS file (in .github/) naming the reviewers, so GitHub asks them automatically. Ask Claude to write it from your group's list of reviewers.
  4. Open a small pull request of your own, for example a clearer description for one skill. Try to merge it before anyone has approved it. What happens?
  5. Have the named reviewer approve it, then merge.
Proof
A pull request that could not be merged until a named reviewer approved it.
Watch for
  • "A rule in the README saying 'get a review' is enough." It is a habit, not a guard. A branch rule is enforced by GitHub.
  • "Every GitHub plan can enforce this." Check yours: on GitHub's free plan, branch rules are not enforced on private repositories. There, the review is the team's habit and CODEOWNERS only requests it.

Hooks

I can make something happen automatically before or after Claude acts.

Do
  1. Open a session on your presentation-template folder from use-a-skill. Read the "Automatic verification" paragraph in .claude/skills/presentation-slides/SKILL.md. Then ask: "Is there a .claude/settings.json in this repo, and does it have that hook?"
  2. It doesn't. Ask Claude to add this to .claude/settings.local.json (keep any rules already there), and read it before you approve:
    {
    "hooks": {
    "PostToolUse": [
    {
    "matcher": "Write|Edit",
    "hooks": [{ "type": "command",
    "command": "node \"$CLAUDE_PROJECT_DIR\"/.claude/skills/presentation-slides/scripts/lint-slides.mjs" }]
    }
    ]
    }
    }

    Given no file names, the lint reads the edit Claude just made and checks only the new text.

  3. Start a new session so the hook loads.
  4. Predict: you ask "In my-deck, make the first slide's title box 40vh tall." What happens after the edit, and who sees the lint's complaint?
  5. Ask. Watch for the hook's message in the session, and what Claude does next.
Proof
A hook that ran: the lint's message in the session, and the fix Claude made in response.
Watch for
  • "The skill says a hook checks my work, so one does." A description of a hook is not a hook. Look in the settings file.
  • "A hook is a reminder to Claude." It is a program Claude Code runs whether Claude would have thought of it or not. That is the whole point.

Running without you
